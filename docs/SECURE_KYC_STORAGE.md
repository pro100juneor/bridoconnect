# Архітектура захищеного зберігання KYC (паспорт + банківські дані)

> Статус: ПРОЄКТ НА ЗАТВЕРДЖЕННЯ. Реалізація — після погодження власником.
> Вимога власника: конфіденційні дані у закритому сховищі, недосяжні для шахраїв,
> без витоків, ніколи не доступні третім особам.

## Принцип: ми НЕ зберігаємо сирі дані там, де їх можна масово вкрасти

### Рівень 1 — банківські дані: НЕ зберігаємо взагалі (рекомендовано)

Банківські реквізити для виплат вже проходять через **Stripe Connect onboarding**:
IBAN вводиться на сторінці Stripe (не на нашій), зберігається у PCI-DSS-сертифікованому
сховищі Stripe, ми бачимо лише останні 4 цифри. **Дія: нічого не будувати.**
У нашій БД — тільки `stripe_account_id`.

### Рівень 2 — паспортні дані: Stripe Identity (рекомендовано)

Верифікацію особи (фото паспорта + selfie-match) робить **Stripe Identity**:

- документ завантажується напряму в Stripe (наш сервер його не бачить);
- ми отримуємо лише вердикт (`verified` / `requires_input`) і мінімальні поля
  (ім'я, дата народження, країна документа) через API;
- зберігання, шифрування, GDPR-зобов'язання — на боці Stripe (DPA підписується
  в дашборді);
- вартість ≈ €1.30–2.00 за перевірку.
  У нашій БД: `identity_verification_id`, `status`, `verified_at`. Жодних сканів.

### Рівень 3 — якщо колись знадобиться зберігати документи самим (запасний план)

Тільки якщо з'явиться юридична вимога тримати копії:

1. **Окремий приватний Storage-бакет** `kyc-documents` (Supabase), без публічних URL.
2. **Клієнтське шифрування до завантаження**: AES-256-GCM, ключ на файл (DEK).
3. **Envelope encryption**: DEK шифрується майстер-ключем (KEK) у KMS
   (Supabase Vault або AWS KMS, EU-регіон). KEK ніколи не покидає KMS.
4. **RLS**: доступ до метаданих — лише власник запису; сервісні виклики — тільки
   через Edge Function з audit-логом (хто/коли/що відкрив).
5. **Retention**: автоматичне видалення через N днів після завершення перевірки.
6. Бекапи бакета вимкнені; expiring signed URLs (≤60 c) видаються тільки
   Edge Function-ом після перевірки прав.

## Порівняння

| Критерій                  | Stripe Identity + Connect (рівні 1–2) | Власне сховище (рівень 3)     |
| ------------------------- | ------------------------------------- | ----------------------------- |
| Ризик витоку з нашої БД   | ~нульовий (даних немає)               | середній навіть з шифруванням |
| GDPR-навантаження на GmbH | мінімальне (processor — Stripe)       | повне (controller+storage)    |
| Вартість                  | ~€1.5/перевірка                       | розробка + KMS + аудити       |
| Швидкість запуску         | днí                                   | тижні                         |

## Рекомендація

Рівні 1–2: банк — лише в Stripe Connect, паспорт — лише в Stripe Identity.
У власній БД — жодних сирих KYC-даних. Рівень 3 тримаємо як задокументований
запасний план і не будуємо без юридичної потреби.

## План впровадження (після погодження)

1. Увімкнути Stripe Identity у дашборді (потрібен live-режим — задача #22).
2. Edge Function `create-identity-session` + webhook `identity.verification_session.verified`.
3. Міграція: `verification_status`, `identity_verification_id` у `profiles`.
4. UI: екран «Верифікація» з Stripe Identity SDK (веб + Capacitor in-app browser).
5. Позначки «верифікований» на публічних сторінках обох категорій.
