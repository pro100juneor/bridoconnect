# BridoConnect — спецификация перестройки: роли + мерчант-маркетплейс (2026-10-11)

**Статус: ЧЕРНОВИК НА РЕВЬЮ ВЛАДЕЛЬЦА. Код НЕ трогается до утверждения этой спеки.**
Повод: на устройстве стало ясно, что ролевая модель и IA не целостны (спонсор может завести магазин;
экраны не связаны; непонятно, что делает спонсор vs получатель; вёрстка разъезжается; разрешён ландшафт).

## 0. Решения владельца (зафиксированы)

1. Магазин подарков строим **в этом приложении** (не отдельный проект).
2. Магазины ведут **только мерчанты** — новая роль. У спонсора и получателя магазина нет.
3. Маркетплейс = **сторонние продавцы** (модель Prom.ua): много магазинов, у каждого свой.
4. Поток подарка: **спонсор покупает товар → отправляет конкретному получателю**.
5. Товары **физические**; **адрес получателя передаётся мерчанту** только для отправки заказа; спонсор адрес не видит.
6. Мерчантом становятся через **заявку + одобрение админом** (далее — Stripe Connect для выплат).

## 2. Информационная архитектура (НАВИГАЦИЯ ПО РОЛЯМ) — предложение на ревью

Нижний таб-бар и меню профиля разные для роли. (Сейчас — один таб-бар на всех, `AppLayout.tsx:8`.)

**Sponsor (5 табов):** Лента (получатели) · Маркет (магазины) · Ефіри · Активність (отправленные подарки + профинансированные сделки) · Профіль.
**Recipient (5):** Моя сторінка · Мої запити (создать/вести) · Ефіри (вести) · Подарунки (полученные) · Профіль.
**Merchant (5):** Замовлення (заказы) · Товари · Магазин (витрина) · [Ефіри?] · Профіль.
**Admin:** существующий экран `/app/admin` (+ раздел «Заявки мерчантов»).

Меню «Профіль»/«Налаштування» тоже ветвятся по роли (убрать у спонсора/получателя пункты продавца; у мерчанта — добавить магазин/выплаты/заказы).

## 3. Модель данных (миграции) — предложение

### 3.1 Роль merchant

- `profiles.role` check → добавить `'merchant'`: `check (role in ('sponsor','recipient','merchant','admin'))`.
- RPC назначения роли (`048`): merchant НЕ выдаётся самосменой — только через одобрение заявки (SECURITY DEFINER, вызывается админ-флоу).

### 3.2 Заявки мерчантов

- `merchant_applications(id, user_id, business_name, legal_info, contact, status 'pending|approved|rejected', created_at, decided_by, decided_at, reason)`.
- RLS: заявитель видит/создаёт свою; админ видит все и меняет status. При approved — триггер/RPC ставит `profiles.role='merchant'`.

### 3.3 Магазины и товары — привязка к мерчанту + ролевой гейт

- `products.seller_id` и `shop_profiles.seller_id` остаются FK на profiles, но RLS INSERT/UPDATE ужесточается:
  добавить `AND (select role from profiles where id = auth.uid()) = 'merchant'` (сейчас гейта по роли нет —
  `020_shop.sql:43`, `024:36`). Переименование seller→merchant — опционально (терминологически), FK тот же.
- Миграция существующих товаров: если есть товары у не-мерчантов — решить (скрыть/перенести/удалить). См. §7.

### 3.4 Подарок-заказ (бенефициар + адрес)

- `orders` расширить: `beneficiary_id uuid references profiles(id)` (кому подарок; NULL = покупка себе, если оставляем),
  `is_gift boolean default false`, `shipping_address_id uuid` (адрес доставки), `fulfillment_status
'pending|accepted|shipped|delivered|canceled'`, `tracking text`.
- `shipping_addresses(id, user_id, full_name, phone, country, city, street, postal_code, notes, created_at)` —
  адреса получателя. RLS: владелец управляет своими; **мерчант видит адрес ТОЛЬКО через заказ, где он продавец**
  (SECURITY DEFINER view/RPC `order_shipping_for_merchant(order_id)` — отдаёт адрес, если `orders.seller_id=auth.uid()`
  и статус оплачен). **Спонсор (покупатель) адрес НЕ видит.**
- Приватность — критично: адрес получателя раскрывается мерчанту пер-заказно и только после оплаты.

### 3.5 Выплаты

- Мерчант: Stripe Connect онбординг в merchant-разделе; чекаут магазина платит мерчанту (как сейчас платит seller,
  `create-checkout:330`) — логика переиспользуется, но гейтится ролью merchant.
- Получатель: Connect для помощи/эскроу остаётся (Profile recipient-only карта — оставить для recipient).

## 4. Поток «подарок получателю» (новый)

1. Спонсор в Маркете выбирает товар у мерчанта → «Подарувати» → **выбирает получателя** (из избранных/поиска) →
   получатель подтверждает/уже имеет адрес доставки (адрес вводит получатель заранее или по запросу).
2. Чекаут: деньги спонсор → мерчант (Connect destination). Заказ: `buyer_id=спонсор`, `seller_id=мерчант`,
   `beneficiary_id=получатель`, `is_gift=true`, `shipping_address_id`.
3. Мерчант видит заказ + адрес получателя (только свой заказ) → отправляет → `fulfillment_status`/`tracking`.
4. Получатель видит «Подарунки» со статусом доставки; пуш/ин-апп уведомление. Спонсор видит статус (без адреса).
5. Возвраты/споры — отдельный под-поток (переиспользовать dispute-инфраструктуру), этап позже.

## 5. RLS / приватность (сводка инвариантов)

- Товары/витрины: create/update только role=merchant и `seller_id=auth.uid()`.
- Адрес доставки: читает владелец (получатель) и мерчант-владелец оплаченного заказа; спонсор — никогда.
- Заказ: видят покупатель (без адреса), мерчант-продавец (с адресом), бенефициар-получатель (свой подарок).
- Роль merchant ставится только одобрением заявки (не клиентом).

## 8. Этапы (предложение по порядку; каждый — отдельный набор коммитов, конвейер зелёный)

- **Phase 0 — Вёрстка/ориентация + ролевой гейт магазина (быстро, низкий риск):** portrait lock, overflow-guard,
  скрыть продавцовские кнопки у не-мерчантов. Приложение сразу перестаёт «разъезжаться» и путать ролями.
- **Phase 1 — Роль merchant + заявки + админ-одобрение:** миграции (role, merchant_applications), RLS, экран заявки,
  раздел в Admin. Мерчант появляется как сущность.
- **Phase 2 — Ролевая навигация/IA:** разные табы и меню для sponsor/recipient/merchant.
- **Phase 3 — Магазин мерчанта + маркет:** витрина мерчанта как первичная IA (магазины, не плоский каталог),
  управление товарами гейтится ролью.
- **Phase 4 — Поток подарка:** адреса доставки, выбор бенефициара, заказ с beneficiary_id, чекаут, экран «Подарунки»,
  кабинет заказов мерчанта, приватность адреса (RLS/RPC).
- **Phase 5 — Выплаты мерчанта (Connect), уведомления, статусы доставки, возвраты/споры.**

Phase 0 можно делать сразу по «ok». Phases 1–5 — крупные; каждую оформлю под-планом перед реализацией.
